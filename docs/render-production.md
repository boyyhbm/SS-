# NEXUS на Render

## Публичная установка

Владелец уже создал Blueprint и сообщил адреса:

- Web: **https://nexus-web-ylcv.onrender.com**.
- Multiplayer: **https://nexus-multiplayer.onrender.com**.

Оба сервиса запущены, PostgreSQL доступна. На этих адресах прошли настоящая регистрация, сохранение библиотеки, одиночная игра, приватная WSS-гонка двух независимых браузерных процессов, оба серверных финиша и повторное лобби. После фактического перезапуска Web и Multiplayer подтверждены новые instance IDs и точное совпадение сохранённых данных. [Отчёт](render-public-tests.json). Посетителю достаточно открыть Web URL; запускать среду разработки не требуется.

## Конфигурация проекта

[`render.yaml`](../render.yaml) создаёт в Frankfurt:

| Ресурс            | Настройка                                                                                 |
| ----------------- | ----------------------------------------------------------------------------------------- |
| nexus-web         | Платный Starter, 1 instance, Next.js production, HTTPS; диск `/var/data`, 1 GB            |
| nexus-multiplayer | Платный Starter, 1 instance, отдельный Colyseus, WSS                                      |
| nexus-database    | Платный basic-256mb, PostgreSQL 16, 5 GB; внешние подключения запрещены `ipAllowList: []` |

Free не используется: постоянно доступный игровой процесс и долговременная БД не должны зависеть от бесплатного trial. Владелец запустил создание перечисленных ресурсов в своём Dashboard. Актуальную стоимость и состояние оплаты показывает Render; агент не проверял billing аккаунта. При подключении другого существующего проекта сначала сверить конфигурацию и сохранить его backup.

Blueprint подключён к `boyyhbm/SS-`, ветка `main`. Dashboard ранее отклонил `maxShutdownDelaySeconds` у Web с диском; поле удалено. Сетевые разрешения применены, владелец подтвердил device login официального Render CLI; авторизация хранится в закрытой конфигурации CLI, не в репозитории.

Образы уже имеют production-скрипты; пути `deploy/railway/Dockerfile.*` сохранены для повторного использования прежних Dockerfile. Имя каталога не меняет их работу на Render. Никаких серверов Node на телефоне или компьютере посетителя запускать не нужно.

## Первый deploy и сохранение данных

Первый deploy использовал режим подготовки. Перед включением проведена проверка **существующей локальной** БД: все таблицы личных данных пусты, пользователей/сохранений/библиотек/друзей/матчей нет, загруженных файлов нет, активных rate limits нет. Перенос приватных записей не требуется. Исходная БД и её полная закрытая резервная копия сохранены. Только четыре опубликованные карточки игр сохранены в `prisma/catalog.snapshot.json` с прежними ID, датами и всеми полями. В чистой отдельной БД проверено точное совпадение этих записей и сохранение административных изменений при повторном seed: [отчёт](render-catalog-seed-tests.json).

Текущий Blueprint задаёт два фактических origin и `NEXUS_LIVE=1`. Pre-deploy успешно применил четыре существующие миграции и идемпотентный seed без создания пользователей. Если для другой установки нужно переносить существующие аккаунты, сначала установить `NEXUS_LIVE=0` в Blueprint: подготовка отвечает 503 для страниц/регистрации и не запускает миграции или игру.

**Для новой установки:** первоначальный `generateValue: true` выдал 44 символа, а production-валидатор требует не менее 64. В текущей установке это исправлено: через защищённый API Render сохранены два независимых случайных 96-символьных hex-ключа. Общий `MULTIPLAYER_SECRET` находится в группе `nexus-production`, отдельный `NEXTAUTH_SECRET` — только у Web. В новой установке перед Live следует аналогично сохранить длинные ключи в настройках хостинга и пересоздать deployment. Значения не печатаются и не помещаются в Git, публичные переменные или чат; проверка длины не ослаблялась. Не менять рабочие ключи при обычном обновлении.

`DATABASE_URL` берётся из **внутреннего** connectionString managed PostgreSQL, Web→Multiplayer — из private hostport. Production-проверка отклоняет внешний DB URL, публичный control URL и загрузки вне диска. Наличие настоящего mount `/var/data` проверяется по таблице монтирования Linux.

Следующие инструкции нужны для будущего переноса источника с личными данными. Для текущего пустого источника они не требуются. Приватная проверенная копия находится вне Git; перед будущим переносом сделать свежую:

```bash
npm run production:backup -- /absolute/private/backup-directory
```

Render PostgreSQL нельзя открывать всему интернету ради переноса. Доверенный сопровождающий добавляет свой SSH public key в Render и открывает туннель через уже работающий подготовительный Web:

```bash
render ssh nexus-web --output text -- -N -L 127.0.0.1:55432:<actual-private-db-host>:5432
```

Приватные PG-параметры берутся только из защищённой конфигурации Render и сохраняются локально в отдельном env-файле с правами 600. Для клиента через туннель указать `PGHOST=127.0.0.1`, `PGPORT=55432`, имя базы/пользователя и пароль хостинга. Не отключать проверку host key SSH. Команды PostgreSQL 16 запускаются локально в Docker; нужен Linux host networking:

```bash
docker run --rm --network host --env-file /private/render-restore.env postgres:16-alpine psql -Atc "SELECT count(*) FROM pg_tables WHERE schemaname = 'public'"
```

Восстанавливать только если целевая БД пуста (результат 0):

```bash
docker run --rm -i --network host --env-file /private/render-restore.env postgres:16-alpine pg_restore --no-owner --no-acl --single-transaction --exit-on-error < /private/backup/database.dump
```

Не применять `--clean`, reset или импорт поверх живой базы. Сохранить `_prisma_migrations`, все ID/password hashes, библиотеки, контроллеры, saves, друзей и результаты; проверить количество таблиц, число строк и отпечатки содержимого. Локальное восстановление всех 23 таблиц ранее проверено, но перенос в Render ещё **не выполнялся**.

Передать собственный архив uploads в постоянный диск через зашифрованный SSH stdin:

```bash
render ssh nexus-web --output text -- -T 'mkdir -p /var/data/uploads && tar -xzf - -C /var/data/uploads' < /private/backup/uploads.tar.gz
```

Команды SSH сверены с исходниками [официального CLI](https://github.com/render-oss/cli) `7129791ee688c7fb0622bef2f571298c1b682e9c`; на аккаунте Render они ещё не проверены. Если план ограничивает forwarding/SSH, сначала выяснить поддерживаемый private transfer, сохранив запрет внешней БД. Приватную исходную резервную копию не удалять.

## Включение NEXUS

Значения текущей установки уже объявлены в группе **nexus-production** в `render.yaml`:

- `NEXUS_WEB_ORIGIN` — `https://nexus-web-ylcv.onrender.com`.
- `NEXUS_MULTIPLAYER_ORIGIN` — `https://nexus-multiplayer.onrender.com`; код преобразует его в WSS для браузера.
- `NEXUS_LIVE=1`.

Теперь эти три значения управляются Blueprint; при смене домена или режима нужно менять их в `render.yaml`, затем синхронизировать и пересобрать сервисы. Адреса взяты у владельца, не угаданы по имени. Для Web и Multiplayer нужен **rebuild и deploy** после смены параметров. Web встраивает WSS origin в собранную CSP-политику; одного runtime restart недостаточно. SDK получает адрес подключения из подписанного сервером билета.

Pre-deploy сериализует `prisma migrate deploy` через PostgreSQL advisory lock; Web дополнительно выполняет идемпотентный seed без перезаписи пользовательских данных. Сбой останавливает развёртывание. После импорта существующих миграций остаются только действительно новые. Регистрация доступна только после живого запуска.

Health Web — `/api/health`, готовность Multiplayer — `/health`. `/live` используется для handover: новый процесс ждёт ownership, старый получает SIGTERM и освобождает lease. Внешний monitoring должен проверять `/health`, а не только `/live`. Один активный игровой процесс; данные завершённых матчей сохраняются, незавершённая гонка при перезапуске становится ABORTED без выдуманного победителя. Диск Web допускает краткое прерывание при обновлении.

## Публичные проверки и обновления

После запуска использовать только фактический HTTPS адрес:

```bash
NEXUS_PUBLIC_URL=<actual-Web-HTTPS-origin> npm run test:production -- before
```

Проверяются два независимых аккаунта, Secure cookie, библиотека/избранное, одиночный круг/save, друзья, приглашение, WSS-гонка и два серверных финиша. Затем **реально перезапустить оба сервиса** и выполнить `after-restart` с приватным state-файлом первого запуска. Тест требует смены обоих instance IDs и совпадения сохранённых данных. Оба этапа выполнены на текущем публичном сайте. Если тестовая облачная среда требует HTTP proxy, передать `NEXUS_TEST_USE_PROXY=1`; нормальная проверка TLS сохраняется. Раздельные процессы Chromium используют SwiftShader, DPR 0.15 и спокойный тестовый темп управления; физика, финиш и серверный лимит не меняются. Это не замер FPS и не проверка физических контроллеров.

При проверенном перезапуске Multiplayer первая попытка исчерпала 120 секунд ожидания ownership. Render повторно запустил процесс, готовность восстановилась в 13:08:50 UTC после запроса в 13:05:18 UTC. Результаты завершённых гонок не потеряны. Следить за `/health`; краткая доступность `/live` не означает готовность гонки. Активные комнаты при перезапуске не сохраняются.

`autoDeployTrigger: checksPass` связывает публикацию main с проверками [GitHub Actions](../.github/workflows/ci.yml). Первое автоматическое развёртывание commit `2301b6d` было запущено Render по `new_commit` после успешного CI, но остановилось на слишком коротких ключах. После исправления ключей тот же commit успешно развёрнут через API. База при обновлениях не пересоздаётся. Последнюю наблюдаемую публикацию и её проверки фиксирует [статус](production-status.json).

API Render подтвердил PostgreSQL `available`, `ipAllowList: []` и PITR `AVAILABLE` с 25 октября 2026, 11:17:05 UTC. Диск Web действительно подключён в `/var/data`, 1 GB; при первоначальной проверке снимков диска ещё не было. Пробное восстановление именно managed production backup не выполнялось; локальная копия отдельно восстановлена и проверена. Не считать наличие PITR подтверждением успешного restore drill.

После очистки шести проверочных аккаунтов также создан managed logical export PostgreSQL от 13:19 UTC. API выдал закрытую ссылку для скачивания; её значение не сохранено в Git и не опубликовано. Загрузка архива и пробное восстановление этого export не проверялись. Для commit `623019a` успешно прошёл новый CI (75 unit и 16 браузерных тестов); Render автоматически развернул его в обоих сервисах, после переключения оба readiness endpoint вернули 200. Этот commit меняет только тестовые инструменты и документацию, без изменений модулей приложения. Обновление самого отчёта помечено `[skip ci] [skip render]`, чтобы не перезапускать рабочие сервисы ради документации.

## Администратор production

Сначала зарегистрировать личный аккаунт через публичный сайт. В защищённом Shell сервиса **nexus-multiplayer** владелец Render может назначить ему роль:

```bash
node --import tsx scripts/admin.ts your-email@example.com
```

Заменить адрес на email уже созданного аккаунта. Пароль не нужен и не передаётся в команду. После назначения заново войти в NEXUS и открыть `/admin`. Стандартного администратора и публичного способа повышения роли нет. В ходе публичной проверки реальные аккаунты владельца не повышались и не изменялись.

Свой домен: открыть `nexus-web` → Settings → Custom Domains → Add Custom Domain, указать принадлежащий владельцу домен и внести именно показанные Render DNS-записи. Дождаться TLS-сертификата. Поменять `NEXUS_WEB_ORIGIN` в `render.yaml`, синхронизировать Blueprint, пересобрать Web и развернуть оба сервиса, затем повторить публичные проверки. Для собственного WSS-поддомена аналогично добавить домен к Multiplayer и поменять `NEXUS_MULTIPLAYER_ORIGIN`.
